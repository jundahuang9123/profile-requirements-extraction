Reference requirements compared

The 75 reference rows in benchmark-data (repo snapshot 69f3c26): mobilityDCAT-AP 40, HealthDCAT-AP 16, StatDCAT-AP 7, GeoDCAT-AP 7, DCAT-AP-JRC 5. EPOS has no enumerated rows and is left out. Each row is traced to what its published profile did, relative to the DCAT-AP release that profile extends.

40of 75 rows

are metadata-content needs. 27 are rules for the profile itself (principles, alignment, obligations, documentation) and 8 concern systems or processes. All 7 Geo rows and 24 of 40 Mobility rows are of this kind.

28of 40 content rows

were met with a new class or property: 17 minted in the extension’s own namespace, 11 imported from other vocabularies (DCMI Terms, DQV, DPV, CSVW, VANN, a later DCAT-AP).

6of 40 content rows

were met by constraining (3) or expanding (3) existing terms. Most constraining is asked for as profile rules instead (obligations, value lists, usage notes: Req-15, 32, 33, 34, 37).

5 + 3

restate the base: Req-18, Req-35, S-7, JRC-2, JRC-5. Three more would under a later base: Req-20 with DCAT-AP 3.0.0, JRC-1 and JRC-4 with 2.0.1.

7of 12

Mobility rows that needed new terms cite the CMC, an earlier NAP metadata catalogue. Health rows mostly cite law (10 of 16); Stat rows working-group discussion; JRC rows catalogue practice.

Before vs after

Mobility rows were written before the design: one “should” sentence, importance in its own column, often compound. Stat, Health and JRC rows were written with or after it, as rationale for adopted terms, and are near-atomic. The JSON paraphrases make all 75 look alike.

Three side findings

The base version decides the count

Under the base each profile cites, 5 content rows restate it. Under a later DCAT-AP release, 3 more would: dct:creator and dct:isReferencedBy (JRC-1, JRC-4) are in DCAT-AP 2.0.1; dcatap:applicableLegislation (Req-20) is in 3.0.0.

Profiles add and drop terms no row names

mobilityDCAT-AP: 2 of 12 minted properties (application-layer protocol, communication method) come from CMC elements, not from a Table 1 row; 19 imported contact and address terms, mostly marked as analogue to GeoDCAT-AP, match no row directly. It also drops 41 optional or recommended DCAT-AP 2.0.1 properties; Req-15 asks for a common essential set but names none. HealthDCAT-AP: 2 of 14 minted properties (number of records, retention period) are outside the 16 curated rows.

12 rows are reuse or alignment rules

Mobility Req-5, 9, 10, 11, 12, 13, 16 and Geo G-1 to G-5 say which vocabularies to reuse or align with. They are reuse questions (RQ2), not needs to extract; all 12 got no term-level response.

Method and limits

Base per case
DCAT-AP 2.0.1 (Mobility), 3.0.0 (Health), 1.1 (Stat, Geo, JRC), as the paper pins them. “New” means the URI is in no class of that base; “on a new class” means the base has the term elsewhere.
Design sources
mobilityDCAT-AP 1.0.0 (repo HTML, incl. Annex A.2 additions and Annex B CMC mapping); D6.2 §5.2–5.3; StatDCAT-AP 1.0.0 §7.2; GeoDCAT-AP 1.0 §1.1, §4.1–4.3; the JRC SDSVoc 2016 paper.
Response codes
New class / new property (minted or imported) · new code lists · expand an existing term (base term on another class, or a base code list extended) · constrain an existing term (obligation raised, values restricted, usage narrowed) · already in base · no term-level response · proposed or not addressed. One main response per row; all term effects are listed per row.
Levels
Content = information a record should carry. Profile = rules about the specification. System = catalogue, validation, exchange or review behaviour.
